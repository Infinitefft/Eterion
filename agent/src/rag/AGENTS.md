# RAG 模块开发约定

适用于 `agent/src/rag/`，继承仓库及 `agent/AGENTS.md`。本文件仅保留整体约束；**实现或修改入库、切分、Embedding 准备逻辑前，必须阅读 [INGESTION.md](INGESTION.md)**，按其中已确认的规则执行。方案变化时同步更新设计文档，避免在两处重复维护细节。

## 定位与范围

- 服务于前端岗位秋招展示，优先完成可运行、可解释、可验证的最小充分方案，用户需参与核心设计与实现。
- 采用 Agentic RAG：模型自主调用 `knowledge_search`，通过 `query` 参数提供检索文本；工具完成查询 Embedding 与检索，结果通过现有 ToolMessage 机制返回模型。不额外增加问题提取模型调用。
- 检索默认覆盖当前登录用户全部知识库中已完成索引的资料，不要求用户选库，不增加分类路由；由服务端限定用户范围，跨库统一排序取 Top K，保留来源信息。
- 第一版建立基础向量检索基线，暂不加入 HyDE、BM25、混合检索、重排、多查询或复杂 Parent-Child Retrieval。
- 存储采用 Docker 中启用 pgvector 的 PostgreSQL；业务表与 RAG 表共用同一个数据库，不单独部署向量数据库。本机迁移与 Chunk 建表已完成，具体结构和验证结果见 [INGESTION.md](INGESTION.md)。
- Agent 负责 RAG 索引数据的生成、写入与检索，Go 负责业务文件和归属权限；通过业务文件 ID 关联。迁移与存储细节见 [INGESTION.md](INGESTION.md)。
- Embedding 使用阿里百炼 `text-embedding-v4` API，第一版采用 1024 维；文档与查询使用同一模型和维度，不自行替换为开源 Qwen3-Embedding 型号。
- OSS 上传和业务文件记录保存成功后，立即触发 Agent 执行切分、Embedding 和入库，先跑通整体成功路径；第一版不增加重试、补偿、任务恢复或消息队列，实际失败如实报错。
- 前端识别 `knowledge_search` 工具，展示命中文件；点击来源后通过 Go 的 GET 接口读取原文，依据工具返回的原文偏移量定位并高亮。具体契约见设计文档。

## 模块边界

- RAG 专属代码尽量集中在本目录，包括文档处理、切分、Embedding、索引、检索、`knowledge_search` 工具定义、专属提示词、结果展示转换及相关类型，不按通用技术分类分散到 `../tools/` 等目录。
- 外部公共模块只做必要接入：`../runtime/` 注册工具并沿用通用执行与事件机制，公共展示入口调用本目录的结果转换。配置沿用项目统一加载入口，RAG 专属配置结构与校验可就近定义；仅必要的跨服务字段进入公共协议，不另建重复基础设施。
- 复用既有 Go 文件管理、OSS 与权限链路；涉及前端展示、Go 接口或数据库迁移的配套改动仍放在各自项目的对应模块。
- 按实际职责模块化，保持清晰类型和浅调用链；不为未来能力增加占位文件、无意义 wrapper 或多层抽象。

## 实现与交付

- 修改前检查现有代码与依赖，优先使用成熟库；采用前核对真实版本、API 与能力限制，不自行重写 Markdown AST Parser 或已有切分算法。
- 第一版 Markdown 按标题切 Section，再在各 Section 内递归切分并添加 overlap；TXT 对全文递归切分。代码块、列表、表格等结构保护留待后续优化，不作为本版验收条件。
- 遵循设计文档中完整 Embedding 输入预算及来源追溯要求；不能静默丢内容、伪造原文位置或把估算当作精确 token 计数。
- 分步说明数据流、关键取舍和修改文件，遵循上级协作与测试约定。区分设计、已实现和已验证的能力，如实记录限制及验证结果。
