# Memory 模块开发约定

## 模块目标

实现 Agent 会话上下文的持久化、恢复、运行时自动压缩和用户主动压缩。

完整链路：

```text
读取已有上下文
→ 补充新消息
→ Agent 执行与自动压缩
→ 获取最终上下文
→ 保存到业务数据库
→ 后续恢复并继续运行
```

本模块负责会话级上下文，不涉及跨会话长期记忆。

项目用于个人秋招展示。优先保证实现清楚、可运行、可解释，不穷举低概率边界，不引入收益不明确的复杂架构。

本文描述模块目标和开发约束，不代表相关能力已经实现。

## 职责边界

- **Agent**：上下文组装、压缩策略、消息序列化与恢复。
- **Go 后端**：鉴权、会话归属校验、业务数据读写、运行状态管理和流式事件转发。
- **PostgreSQL**：保存原始聊天记录和 Agent 上下文。
- **前端**：展示原始聊天正文，提供主动压缩入口和必要的操作反馈。
- **监控平台及其数据库**：完全独立，不参与任何业务逻辑。

Go 不负责决定模型使用哪些上下文，也不负责摘要生成策略。

## 上下文存储

在现有 `messages` 表增加可空的 `agent_context JSONB` 字段，不新建摘要表。

每轮成功结束后，将最终完整上下文写入本轮 assistant 消息，无论本轮是否发生压缩。

字段包含：

- 最新摘要，如有。
- 压缩时保留的近期消息。
- 后续新增的模型消息、工具调用和工具结果。
- 本轮最终回答。

摘要作为数组中的消息保存，不单独建立历次摘要记录或关联链。

使用框架支持的序列化方式，保留消息类型、ID、工具调用参数和关联信息，不能只提取 `role` 与 `content`。

现有 `content` 字段继续保存聊天正文，不覆盖为摘要。用户消息、未成功完成的助手消息及旧记录的 `agent_context` 可以为空。

## 上下文加载与恢复

通过 Go 内部接口读取数据，由 Agent 恢复并组装上下文。

规则如下：

1. 查找当前会话、本次运行之前，最近一条成功且 `agent_context` 非空的 assistant 消息。
2. 恢复其完整消息数组。
3. 补充该记录之后、截至本轮用户输入的新增消息。
4. 没有有效上下文时，从原始聊天历史组装。

沿用现有历史状态筛选规则，不顺手改变失败、取消消息的产品语义。

不得重复追加已经包含的历史、本轮用户输入或上轮回答。

## 运行时自动压缩

优先复用 LangChain 内置 `summarizationMiddleware`：

- 每次模型调用前检查是否需要压缩。
- 压缩较早消息，保留近期窗口。
- 复用框架的工具消息配对、状态替换和后续消息追加。
- 再次触发压缩时，将旧摘要与较早消息合并为新摘要。
- 主 System Prompt 独立配置，不参与历史摘要。

结合实际模型设置触发预算、近期窗口、摘要输入上限和摘要 Prompt。预算考虑主 System Prompt、工具定义、输出预留和安全余量。

摘要应保留任务目标、用户约束、已确认信息、已完成操作、重要结果和未完成事项。

不手写新的 Agent 循环，不自行维护另一份实时消息数组。

## 上下文交付与持久化

从框架最终状态取得完整消息数组，不从正文流和展示事件重新拼接。

每个 Run 独立接收上下文，避免复用 Agent 实例时不同会话互相覆盖。

Runtime 确认成功后，通过内部协议将上下文交给 Go。上下文、assistant 消息完成状态与 Run 完成状态应在同一数据库事务中提交。

内部上下文不作为普通聊天内容发送给前端。

## 用户主动压缩

提供独立的主动压缩入口：

```text
用户发起
→ Go 鉴权并确认会话空闲
→ Agent 加载上下文
→ 跳过自动触发阈值，执行压缩
→ 保存压缩结果
→ 返回操作结果
```

- 与自动压缩复用同一套摘要逻辑。
- 不启动普通问答或工具执行循环。
- 不新增普通用户消息或助手回答，不修改聊天正文。
- 会话运行中不允许并发执行主动压缩。
- 无可压缩内容时返回“无需压缩”。
- 保存位置必须与上下文实际覆盖范围一致，避免后续恢复时重复追加消息。

## 异常与超限兜底目标

以下能力属于模块范围；目前已有代码实现，尚待真实模型与数据库联调，不能将编译通过视为验证完成：

- 摘要失败时，不将错误文本作为有效摘要替换上下文。
- 摘要请求明确因上下文超限失败时，截断最旧部分，再尝试一次压缩。
- 截断保护主 System Prompt、本轮用户请求和工具调用配对。
- 网络、鉴权等其他错误不触发截断。
- 兜底仍失败时明确结束，不无限重试。
- 摘要成功后主模型仍超限时，返回明确错误，不增加复杂的自动恢复流程。
- 截断不删除原始聊天记录，并提供必要的信息舍弃提示。

当前通过版本化 pnpm 补丁传播内置摘要异常，并在模块内禁用静默裁剪、处理一次显式截断重试。升级依赖时需要重新核对这些行为。

## 不做的事情

- 不使用监控数据库存储或恢复业务记忆。
- 不引入独立记忆数据库、消息队列或其他额外基础设施。
- 不实现运行中断点续跑、崩溃后精确恢复工具执行。
- 不维护历次摘要与原始消息的逐条映射。
- 不实现跨会话长期记忆、RAG、向量检索或复杂记忆淘汰。
- 不为展示技术复杂度重写框架已有能力。
- 不重构与本模块无关的功能。

## 协作与验证

用户需要参与记忆核心设计和关键实现。修改前解释数据流与取舍，将代码拆成便于理解和 Review 的改动。

允许围绕需求修改 Agent、Go 内部接口、数据库模型和迁移，以及主动压缩所需的前端入口；不扩大到无关功能。

遵循现有 Agent 开发约定：不主动新增或运行测试脚本，执行必要的类型或编译检查，实际联调由用户安排。不能将类型检查通过视为端到端验证成功。

验证应覆盖：

- 原始历史加载、已保存上下文恢复，以及消息不重复。
- 运行中压缩后继续调用模型和工具。
- 保存并恢复摘要及其后的新增消息。
- 主动压缩和无需压缩的情况。
- 失败保护及有限的超限兜底。
- 原始聊天展示不受影响。
- 业务运行不依赖监控平台。

尚未实现或验证的能力必须明确标记，不得作为已完成成果描述。
