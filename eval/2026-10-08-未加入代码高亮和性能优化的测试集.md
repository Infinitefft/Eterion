## 主场景：新会话中的同一条流式回答

新建空会话，录制一条 AI 回答从前期到后期的输出，降低历史消息对分析的干扰。用户按输出前、中、后期选取 Markdown 组件事件。

观察到的组件层级：

```text
ChatMessageList
└─ AssistantMessage
   └─ AgentRunTrace
      └─ Markdown
```

该层级是组件关系，不是浏览器任务边界。Task 范围需在 Main 中核对。

### 正文变化的有效样本

| 阶段 | Timestamp（录制时间轴，ms） | Markdown Duration（ms） | Changed Props |
| --- | ---: | ---: | --- |
| 前期 | 8,082.6 | 14.60 | `children`、`remarkPlugins`、`rehypePlugins` |
| 中期 | 15,183.7 | 21.40 | `children`、`remarkPlugins`、`rehypePlugins` |
| 后期 | 23,181.3 | 53.30 | `children`、`remarkPlugins`、`rehypePlugins` |

三个样本均显示正文 `children` 变化，属于本次目标场景。后期单次组件耗时约为前期的 3.65 倍。这个比例只是所选样本之间的比值，不是平均退化比例，也不是优化收益。

Timestamp 是录制时间轴位置，不是发送消息后的等待时间；前、中、后期是用户根据本次输出过程划分的阶段，不代表已测量的正文长度档位。

### 后期的另一条事件：未显示正文变化

| Timestamp（ms） | Markdown Duration（ms） | Changed Props |
| ---: | ---: | --- |
| 23,307.5 | 42.10 | 仅 `remarkPlugins`、`rehypePlugins`，未列出 `children` |

这个事件不能替代上表的后期正文变化样本。它表明当前回答还存在正文未显示变化但组件仍执行的情况。具体触发原因需结合代码确认，不能直接归为历史消息更新。

两组插件配置的提示均为：`Referentially unequal but deeply equal objects. Consider memoization.`，即引用不同但深层内容相同。父组件更新也可能导致子组件执行，不能仅凭该提示认定插件数组是唯一触发原因。

### 后期 Main 轨道

截图选中区间约为 23.14～23.28 秒，Summary 显示：

| 分类 | 区间累计耗时 |
| --- | ---: |
| Scripting | 131 ms |
| Rendering | 4 ms |
| Painting | 3 ms |
| System | 2 ms |
| Total | 141 ms |

分类值为界面取整显示，因此相加可能与 Total 略有差异。141 ms 是所选区间统计，不是单个 Task 的时长。Main 中可见长任务标记，当前主要开销在 JavaScript 执行。

悬浮提示中的 `Animation frame fired: 51.39 ms (self 6 μs)` 是该事件的耗时，不能误写为选中区间或另一条 Markdown 事件的时长。

## 补充场景：关闭高亮后仍存在的重复更新

此部分来自较早的另一组录制，不与新会话样本合并计算。

- Main 中选中过一个 **61.40 ms** 长任务，自身耗时 0.39 ms；分类约为 Scripting 51 ms、System children 8 ms、Rendering 1 ms、Painting 1 ms。
- 约 7,320～7,373 ms 的列表渲染区间可见多个 Markdown 条目。
- 其中一个 Markdown 在 7,320.4 ms 开始，耗时 **20.10 ms**；Changed Props 仅列出两个插件配置，没有列出 `children`。
- 用户逐个检查该组 Markdown 后，报告均只显示两个插件配置引用变化。

这组证据支持“未变正文参与重复渲染”的排查方向，但截图不能唯一识别每个实例对应哪条消息。它与主场景的“同一条增长正文更新成本”是两个需要分别验证的问题。

## 当前结论与限制

1. 关闭代码高亮后仍观察到长任务，不能称为“去掉高亮后没有预警”。
2. 同一条回答正文变化的三个样本中，Markdown 更新耗时从 14.6 ms、21.4 ms 增至 53.3 ms，支持继续排查随内容增长增加的处理成本。
3. Duration 是组件事件耗时，可能包含 Markdown 解析、插件处理及 React 节点生成等工作，不能直接称为纯解析耗时。
4. 截图尚不能单独证明每次均全文重解析，也不能推导算法复杂度；需检查实际处理入口或增加解析计时。
5. 每阶段目前只有一个选定有效样本，没有平均值、P95、长任务总数或多轮统计；不能从中得出稳定性能上限。
6. 本地开发模式、调试记录和输入差异会影响结果；最终优化收益需使用同条件回放，并在生产构建下复核。
7. 本记录不包含开启高亮时的 42.4 ms 等其他样本，避免混淆测试条件。

## 后续对照方法（待执行）

1. 保存固定 Markdown 正文及确定的分片序列、发送间隔。覆盖段落、列表、代码块等双方支持的语法。
2. 固定设备、构建、CPU/网络设置、插件配置与按帧调度；保持高亮关闭。
3. 对照现有方案与稳定块 + 活动块方案，避免同时改变消息级缓存、高亮策略和更新频率而无法区分收益。
4. 分别记录解析累计耗时、单次组件更新耗时、长任务数量与最大时长，并核对最终内容一致性。
5. 解析耗时通过解析入口计时获取；组件耗时通过 Performance 获取，两种指标分开报告。
6. 每种方案重复运行，报告样本数量与波动；保留优化前后原始 trace。当前未保存原始 trace，也未将截图复制入仓库。
